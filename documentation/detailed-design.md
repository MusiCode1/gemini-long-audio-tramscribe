# תכנון מפורט למערכת תמלול מקבילי

מסמך זה מפרט את התכנון של הרכיבים המרכזיים במערכת התמלול המקבילי, בהתבסס על ארכיטקטורת "תור משימות עם Pool של Workers".

## 1. קונפיגורציה
- נוסיף פרמטר חדש לפונקציה `transcribeAudioFile` בשם `maxConcurrentRequests`.
- ערך ברירת המחדל יהיה `3`.
- פרמטר זה יקבע את גודל ה-pool של ה-workers.

## 2. מנגנון ניהול תור ו-Workers
- ניצור פונקציה אסינכרונית חדשה, לדוגמה `processQueue`, שתנהל את התהליך.
- הפונקציה תיצור מערך של `totalChunks` משימות, כל משימה היא אובייקט המכיל את אינדקס המקטע (`chunkIndex`).
- ניצור pool של workers (למשל, מערך של promises). גודל ה-pool יקבע על ידי `maxConcurrentRequests`.
- כל worker יהיה פונקציה אסינכרונית שמסוגלת לקחת משימה מהתור, לעבד אותה (העלאה, תמלול, מחיקה), ולהחזיר את התוצאה.
- נשתמש בלולאה (`for...of` על מערך המשימות) כדי להקצות משימות ל-workers פנויים. `Promise.race()` יכול לעזור לנו לזהות מתי worker מתפנה.

## 3. מנגנון איחוי תוצאות
- ניצור מערך תוצאות מראש בגודל `totalChunks`, מאותחל בערכים ריקים (למשל, `new Array(totalChunks)`).
- כאשר worker מסיים לעבד מקטע, הוא יכניס את התמלול שהתקבל למערך התוצאות במיקום המדויק לפי ה-`chunkIndex` המקורי.
- בדרך זו, גם אם המקטעים מסיימים את העיבוד בסדר שונה מהסדר המקורי, התוצאות תמיד יישמרו בסדר הנכון.
- בסיום כל המשימות, נעבור על מערך התוצאות ונתפור את כל התמלולים יחד באמצעות פונקציית `stitch` הקיימת, בדיוק כפי שנעשה בקוד הסדרתי.

## 4. מנגנון דיווח התקדמות
- נצטרך לשנות את האובייקט `TranscriptionProgress` כדי לשקף את המצב המקבילי.
- נוסיף שדה `completedChunks` שיספור כמה מקטעים סיימו את העיבוד בהצלחה.
- ה-callback `onProgress` יקרא בכל פעם ש-worker *מסיים* משימה.
- ההודעה למשתמש תשקף את מספר המקטעים שהושלמו, לדוגמה: `מתמלל... הושלמו ${completedChunks}/${totalChunks} מקטעים`.
- את עדכוני הסטרימינג (`streamedChunkText`) מכל worker נצטרך לנהל בזהירות. אפשרות אחת היא להציג רק את הסטרימינג של המקטע "הכי ותיק" שעדיין רץ, או לוותר על הצגת הסטרימינג המפורט ולהתמקד בהתקדמות הכוללת. **החלטה:** נתמקד בדיווח התקדמות כולל (מספר מקטעים שהושלמו) כדי לפשט את המימוש הראשוני.

## 5. טיפול בשגיאות
- כל worker יעטוף את לוגיקת העיבוד שלו בבלוק `try...catch`.
- אם מתרחשת שגיאה במקטע ספציפי, ה-worker יתפוס אותה.
- נוסיף מנגנון `retry` פשוט: כל worker ינסה לעבד את המקטע עד 3 פעמים לפני שהוא מוותר ומכריז על שגיאה קריטית.
- אם מקטע נכשל סופית, נאחסן אובייקט שגיאה במערך התוצאות במקום התמלול.
- בסוף התהליך, אם מערך התוצאות מכיל שגיאות, נזרוק שגיאה כוללת שתפרט אילו מקטעים נכשלו.
- חשוב לוודא שפעולת ה-`finally` (מחיקת קבצים מהשרת ומהאחסון המקומי) תתבצע גם במקרה של שגיאות.
